# RoboTwin 2.0: асинхронный чанкинг, RTC и бюджет уверенности

Тот же замкнутый цикл, что в `../libero_pro` (`closed_loop.py`, `planner.py`, guidance из `../h1`), на двуручных задачах RoboTwin 2.0 (Easy, `demo_clean`).

- **Модель:** [`SidneyXie/pi05_robotwin`](https://huggingface.co/SidneyXie/pi05_robotwin) — π0.5 в формате LeRobot, мультизадачная; по README 67.9% на 32 задачах Easy.
- **Чанк:** H = 50, 25 Гц, 14 суставов.

## Устройство

У RoboTwin и LeRobot несовместимые зависимости: RoboTwin требует torch 2.4.1, numpy 1.26 и Python 3.10. Поэтому они работают в разных процессах:

- **Симулятор** — отдельный процесс на каждую параллельную среду (`robotwin_server.py`) в собственном окружении `third_party/RoboTwin/.venv`.
- **Модель и цикл** (`scripts/eval_robotwin.py`) — в окружении `../libero_pro/.venv`.
- **Связь** — через unix-сокет (`remote_env.py`, `wire.py`). Массивы передаются байтами, без pickle, поэтому разные версии numpy друг другу не мешают.

Симуляторы одного батча шагают одновременно.

**Эпизоды.** Эпизод i задачи берёт seed 100000 + 1000·i. Неустойчивые сцены пропускаются детерминированно (seed + 1, …). Поэтому все методы видят одни и те же сцены и тот же шум, и сравнение парное.

**Отличия от официальной оценки RoboTwin.**
- Нет экспертной проверки seed'ов: для неё нужен CuRobo, а он подменён заглушкой. Для оценки в суставных координатах CuRobo не нужен, достаточно mplib.
- Инструкция — название задачи. Так же делает обёртка LeRobot, на которой автор чекпоинта получил свои числа.
- Лимит шагов на задачу берётся из `_eval_step_limit.yml`.

## Запуск

```bash
cd experiments/robotwin
bash setup_robotwin.sh        # один раз, ~20–30 мин: RoboTwin, его venv, ассеты (~3 ГБ), модель (9.4 ГБ), проверки
tmux new -s rt
bash scripts/run_night.sh     # на ночь; ход в runs/night.log, итог в runs/report.md
```

**Что делает `run_night.sh`:**

0. **Проверка.** Синхронный режим с s = 50 (протокол автора) на `beat_block_hammer`, 10 эпизодов; по README там 93%. Если успехов меньше 5 из 10, скрипт останавливается.
1. **Сетка.** 8 задач со средним успехом (41–60% по README, лимит 400–500 шагов), по `EPISODES = 50` эпизодов, задержка `D = 6` шагов (240 мс). Конфигурации идут в порядке приоритета:

   | Приоритет | Конфигурации |
   |---|---|
   | P1 | sync s = 50; sync s = 25; naive s = 25; RTC s = 25 (окно до H − s); RTC s = 25 с коротким окном (до d + 5); RTC s = 25 exact |
   | P2 | naive s = 10; RTC s = 10 с коротким окном; бюджет с постоянным $h^*$ (30: λ = 0 и 1; 40: λ = 0.5) |

   RTC s = 25 и sync s = 25 дополнительно пишут энтропию внимания, чтобы потом откалибровать $h^*$ на RoboTwin.
2. **Отчёт** `runs/report.md`: успех по задачам и парная разница с sync s = 25 (95% ДИ).

Каждая пара (конфигурация, задача) — отдельный процесс. Работает ожидание памяти GPU, повтор при OOM и таймаут из `../libero_pro/scripts/stages/lib.sh`. Готовое при повторном запуске пропускается.

**Параметры:** `JOBS` (по умолчанию 2), `EPISODES`, `D`, `TASKS`.

**Холостой прогон без RoboTwin и без модели:**
```bash
EXTRA="--fake-sim --fake-policy" EPISODES=6 RUNS=/tmp/rt_dry bash scripts/run_night.sh
```

## Если что-то не так

- **`Render Error` в `setup_robotwin.sh`.** SAPIEN рендерит через Vulkan, и на сервере нет Vulkan-драйвера NVIDIA: нужен пакет `libnvidia-gl-<версия драйвера>` и `libvulkan1`.
- **Проверка в `run_night.sh` упала.** Смотреть `runs/sanity_sync_s50/beat_block_hammer.log` (ошибки модели) и `runs/sanity_sync_s50/sim_logs/sim*.log` (ошибки симулятора).
